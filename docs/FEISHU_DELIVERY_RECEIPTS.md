# 飞书回执：如何区分未发送、已送达和需要人工核对

此策略仅覆盖本版本的持久通知 outbox，不是对直连测试脚本或飞书服务端行为的保证。

| 最近状态 | 证据与动作 |
| --- | --- |
| `PREPARING` / `PRE_SEND_RETRY` | 还没有发出本次消息 POST。允许按原退避和权限/时效策略重试，不等于必然投递。 |
| `SUBMITTING` | 已持久记录消息意图，不能确认是否到达飞书。等本次回执；过期后转未知，不发第二次。 |
| `DELIVERY_UNKNOWN` | 禁止自动重试或改目的地补发，也不计入真实送达。比起重复或发送改写后的卡片，系统选择可能漏发并保留现场。 |
| `REJECTED` | 应用发送 POST 收到明确 token 失效拒绝（有效响应 `99991663`）；本行终止，不偷偷换 token 发送第二次。检查应用鉴权。其他未核实拒绝码按未知处理。 |
| `DELIVERED` | 应用：成功响应含有效 `om_...` 消息 ID；旧 webhook：明确成功状态码，没有消息 ID。两者均需同一领取的状态和日志事务成功提交；不代表有人已读。 |

同一消息在飞书有时间限制的 UUID 去重保护，不代表永久去重，也不证明重复请求会返回原消息 ID。[应用发送接口](https://open.feishu.cn/document/server-docs/im-v1/message/create)。本版本不依赖该时间窗口：消息 POST 后响应丢失、无有效消息 ID、5xx、返回处理中或 JSON 字段重复（即使最后一个看似成功）等，应用发送、原消息回复和旧 webhook 一律不自动重发。通过时间窗口内或窗口外都不能把未知变成“已送达”。

## 人工核对（不触发发送）

1. 使用 `get_notification_logs(status="DELIVERY_UNKNOWN")` 找到记录，再按 `outbox_id` 读其全部尝试。看原始 `chat_id`、`outbox_submission.started_at_utc`、`operation`、`reply_to_message_id` 及 `body_sha256`；旧数据可以没有这些字段。数据库保存最终发送内容的规范 JSON 摘要；webhook 不存 URL、签名或 token。提交意图本身不是消息回执。对时效耗尽的 SparkX 页，若最后检查在意图提交后但消息 POST 前阻止投递，记录为 `SKIPPED` 和 `aborted_before_post=true`；在能写入决定前崩溃仍保守地视为未知。
2. 对照原群/私聊，回复须检查**原问题所在话题/会话**。核对发送者、时间、原始卡片或文本及实际消息 ID。如果存在 `STALE_DELIVERED`，那是超过租约后才写入的迟到回执线索；不能仅凭旧 worker 成功就覆盖当前行。没有看到消息不等于证明一定没发出。
3. 保留未决记录与核查证据，不改成 `DELIVERED`、不重置为 PENDING、不换 UUID 补发。本版没有提供自动对账或人工解封写入口。需要新通知时另行授权，重新确认当前权限、目的地与有效性。
4. 未知晨报页阻止同批后页越过它；原发送窗口过期后后页正常过期，不影响其他批次。未知广告通知保留原事件的防重复占位，不进入已送达历史。

## 升级与回滚

不改表结构。新增状态使用已有的状态列，意图存储于原有 JSON。先停止**所有**可能派发通知的进程（包括 scheduler、bot 及手工/MCP 派发），备份 MariaDB，核对并记录状态/条数后再统一升级，避免不同版本同时消费。已尝试的旧 `RETRY` / `PENDING` 没有证据证明消息未发送，选中时转为未知；遗留 `SENDING` 租约到期也转未知。旧 `DEAD`、历史回执不批量重写或重放。

代码回滚同样先停派发，保留数据库、JSON 与卷。旧版本不认识新状态，还可能按新事件键为同一广告再建通知；**不要恢复旧版本的自动通知**，直到核对所有未决及遗留尝试、验证抑制重复的兼容方案。不要为了让旧版“看见”队列而把新状态改为 `RETRY`。可以在禁发状态回滚其他只读功能。

离线故障测试用 MockTransport 与独立 SQLite 会话；不是实网送达或 MariaDB 多进程锁验收。即使在意图落库后、真正 POST 前崩溃，也可能保守地进入未知。该策略不承诺“恰好一次”或零漏发。

## 通用应用告警：SKU 范围与切换前核对

- 新的通用规则告警在首次插入时记录版本化的来源范围，重复入队或并发写入不会替旧行“补证”。只有明确的店铺 MSKU 销售事件、或明确携带原 MSKU 和广告编号的商品广告事件才按 SKU 路由。不从消息文本、ASIN、哈希或后来变化的异常记录倒推身份。
- 对这些新 SKU 消息，取得 token 后、提交消息意图前，再查当前店铺授权、通知开关及路由。群消息须与原群、群代次、角色、兜底方式、完整 @ 名单一致；变更后整条留作 `SKIPPED`，不会改群、删加 @ 或“重做”一条。没有目录商品时仍可使用明确的原映射或获准的不带 @ 日报群兜底。原有管理者私聊按对应店铺和事件等级/状态单独核验，不依赖运营群是否仍有负责人。
- 实质广告告警的通用群/私聊副本必须有原店铺、广告类型和活动编号；商品广告还须核对广告编号、当前关联与启用状态。店铺广告授权有效，活动及商品广告状态都须在 90 分钟新鲜期内。不会把 SKU 当活动编号。意图提交本身跨过期限/适用发送时段，也会在 POST 前停止，并保留意图与 `aborted_before_post=true`。仅有活动或 ASIN 证据的群消息，不因此获得 SKU 级 @ 校验。
- 这是**当前仓库数据和本地路由配置**的核验，不是实时查询飞书群成员，更不证明某人已读。未配置成员名册时保留原有显式映射策略；若原群已有核验名册，不能因后来删除名册而放行。数据库及路由文件与飞书 POST 不是分布式事务。应用/租户/凭证轮换必须停派发并重启，不保证运行中更换身份仍能安全使用原 token。
- **未来经批准部署前**，先停止全部生产者/派发入口并等待在途尝试结束或按原回执规则隔离；不要为“清空队列”而发送。备份数据库、配置和卷，以只读方式按来源、接收类型、状态和意图盘点。通用成功目的地的键是 `app:` 加 64 位小写十六进制，仅能识别来源家族。升级前无类型证据的通用**群消息（含非 SKU）和实质广告私聊**，若本可派发，将保留为未发送；可能已提交的尝试仍优先进入原有未知处理。**旧非实质告警的独立管理者私聊沿用旧策略**，不得视为已重新授权；单列这些行，未经核实并妥善处置前保持派发关闭。明确接受可能漏发后再统一切换消费者，禁止新旧 worker 混跑。
- 每小时/隔夜汇总、Chat/MCP 单独审核的副本、晨报、原会话回复与旧 webhook 不套用本规则。保留原行、UUID、终态和未知回执，不重置重发。回滚先停全部派发；旧代码会忽略类型证据，故只能在禁发状态下回滚，直到兼容性及未决队列另行核实。
