# 通知内容与规则

三条通知默认全部开启，可在管理台「通知与报告」调整。每次运行重新读取开关、接收人、阈值和任务说明，无需重启。SparkX Token 和 DeepSeek Key 都保存之前不会运行，也不会留下失败记录。

## 谁来查数据、谁来写

DeepSeek 直接调用 SparkX MCP 查询并撰写（与 WorkBuddy、Claude 接入 SparkX 的方式相同）：

1. 系统打开一个 SparkX 会话，读取 Token 授权的店铺，去掉管理台里「未纳入通知」的店铺。
2. 把 SparkX 原样的只读工具、官方 Skills 目录、店铺目录（含运营）和当前时间交给 DeepSeek，再附上这条通知的任务：统计日期、店铺范围（profileIds）、输出格式，以及管理台里的「任务说明」。
3. DeepSeek 先阅读需要的 Skill（例如 `sparkx-query-ads-performance` 和它要求的 `platform-notes.md`），再自己构造查询；SparkX 的结果原样交给它。
4. 日报和复盘：DeepSeek 写 Markdown，系统把表格转换成飞书表格；内容太长时拆成多张卡片。表格里的「运营」列由系统固定移到最后一列（即使模型写在前面）。最后一行由 DeepSeek 写出需要运营处理的店铺 profileId（日报：须知里点名的店铺；复盘：有异常的店铺），用来 @ 运营，不展示；漏写时系统再用一次不带工具的 DeepSeek 请求从正文中找出。
   日报里缺数据的店铺由系统按这次 SparkX 实际返回的行列出（明细表下方一行，见下文），不由 DeepSeek 自己写：实测时模型自己写的名单漏过店铺，也把有总销售额的店铺写成「暂无数据」。
   日报「指标 | 当日 | 前一日 | 环比」表的环比由系统按同一行的当日、前一日核对：怎么四舍五入都对不上时改成正确值，须知里重复的同一个百分比跟着改（实测时模型把广告花费 -14.4% 写成了 -22.7%）。
5. 实时监控：DeepSeek 返回结构化结果。系统逐条核对：店铺在通知范围内、活动 ID 确实出现在 SparkX 返回中、数字符合阈值；不符合的丢弃。

要求的优先级（所有者要求，2026-11-24）：

1. **SparkX 返回的数据和官方 Skill 的要求第一**：查询方法、指标口径、数据解读，以及 Skill 和结果 `meta.hint` 要求向读者说明的事项（近期的广告订单、广告销售额、ACOS 是暂定值，多店金额是 USD，分页没取完或数据缺失、不足以下结论，相关不等于因果）。
2. **JX 的任务说明和输出格式第二**：写哪些内容、结构、表格和列、篇幅。在不违背第 1 条的前提下照做，冲突时以 SparkX 为准。管理台里的「任务说明」也属于这一级。
3. **从简**：第 1 条要求说明的事项只用一句短话；卡片不写数据来源、生成方式、查询次数和查询或分析过程，不复述口径和公式，标题不带「SparkX」。实时监控的判定阈值在管理台「通知与报告」查看。

## 接收人与 @ 规则

| 通知 | 通知群 | 群内 @ | 私聊 |
|---|---|---|---|
| 08:30 日报 | 发送（默认） | 须知里点名店铺的对应运营（默认） | 总负责人（默认，可多位） |
| 异常复盘 | 发送（默认） | 有问题店铺的对应运营（默认） | 广告负责人（默认，可多位）；对应运营只含其店铺（可选，默认关） |
| 实时监控 | 发送（默认） | 本次新提醒店铺的对应运营（默认） | 广告负责人（默认，可多位）；对应运营只含其店铺（可选，默认关） |

- 总负责人和广告负责人各可选 1–10 位通知群成员，每人都收到私聊（及 Excel）；同一人既是负责人又是运营时只收一份。

- 店铺还没有指定运营时照常发送：表格里标注「未映射运营」，群消息不 @ 任何人。
- 在「店铺与运营」为店铺指定运营后（可多选店铺批量指定），这家店出现问题时群消息顶部显示「对应运营：@某某（店铺A、店铺B）」，只 @ 这次涉及店铺的运营，并写出是哪几家店。店铺名太多、放不下时只保留 @。
- 三条通知各有「群内 @ 对应运营」开关，关掉后照常发送，只是不 @ 人。
- 只 @ 仍在通知群里的成员。消息排队后若运营被更换或移出群，发送时不再 @ 此人，消息照常发出。
- 复盘的「运营私聊」由 DeepSeek 把完整复盘裁剪成只含该运营店铺的版本（不增加内容）。

## 日期与口径

- 店铺报表时区按美西（`America/Los_Angeles`）。08:30 北京时间对应美西前一天下午，日报取美西最近一个已结束的完整日；复盘取截至该日的近 7 日对比前 7 日。
- 多店查询的金额由 SparkX 统一折算为 USD。比率由加总后的基础指标重新计算，不对比率求平均（Skill 的规则）。
- 缺失的数据写「—」，不当成 0。近 7–14 天的广告销售和广告订单仍会因归因回补，报告按 Skill 要求用一句话标为暂定值。
- 订单、销量、销售额都分「广告」和「总」两种，所有通知都写全称（广告订单 / 总订单、广告销量 / 总销量、广告销售额 / 总销售额），不只写「订单」「销量」。

| 名称 | 含义 | SparkX（`get_ads_perf`） |
|---|---|---|
| 广告花费、广告销售额、广告订单、广告销量、点击 | 广告归因（SP、SB、SD 全部广告，按点击日归因，7–14 天内回补） | `factEntity=campaign`：`Spend`、`Sales`、`Conversions`、`Units`、`Clicks` |
| 总销售额、总订单、总销量 | 店铺全部销售，含自然单（店铺报表） | `factEntity=asin`：`TotalSalesAmount`、`OrderCount`、`UnitCount` |
| ACOS / TACOS / CVR / PPC / ROAS | 广告花费 ÷ 广告销售额 / 广告花费 ÷ 总销售额 / 广告订单 ÷ 点击 / 广告花费 ÷ 点击 / 广告销售额 ÷ 广告花费 | 由上面两行计算 |

- 店铺总数据比广告数据更新得晚，也可能缺失（2026-11-24 实测：最近一天的总订单还是 0，而总销量已有数据；个别店铺一直没有店铺总数据）。某店总订单为 0 而总销量大于 0、或总销售额为 0 而广告销售额大于 0 时，日报表格写「—」，由系统在明细表下方说明；全公司的总数只加有数据的店铺，全公司 TACOS = 这些店铺的广告花费 ÷ 它们的总销售额。

## 08:30 广告日报（默认任务说明）

1. 一句话概述：统计日、对比日、监控店铺数、有广告数据和有广告花费的店铺数、金额单位。
2. 全公司核心指标：总销售额、广告销售额、总订单、广告订单、总销量、广告销量、广告花费、ACOS、TACOS、CVR、PPC、ROAS，当日 / 前一日 / 环比。
3. 站点汇总表（监控店铺分布在两个及以上站点时才有；只有一个站点时与全公司指标重复，省略）。
4. 有花费店铺明细：店铺、广告花费、广告销售额、总销售额、广告订单、总订单、广告销量、总销量、ACOS、TACOS、花费日环比、运营（最后一列）。表格下方一行由系统根据 SparkX 返回的行写出，例如「暂无广告数据：昌泉、迈源；暂无店铺总数据：汤宝；各店总订单尚未更新（表中记「—」）。」：
   - 暂无广告数据：查询覆盖了这家店、结果完整（没有分页没取完、没有筛选），但统计日没有广告行；
   - 当日无广告花费：有广告行但花费为 0；
   - 暂无店铺总数据：有广告销售额，但总销售额为 0 或没有返回；总订单尚未更新：总销量大于 0 而总订单为 0。
   SparkX 的结果不足以判定每一家店时（例如分页没取完），保留 DeepSeek 原来写的名单。
5. 须知：2–4 条资深投手口吻的短评（花费集中度、ACOS 偏高、有花费没有广告订单）；缺数据的说明不写进开头和须知，由第 4 条那一行统一列出。

店铺名用目录里的简称；名称只差大小写或标点的 Vendor 账号加「（Vendor）」，避免读起来像同一家店既在表里又在缺数据名单里。

## 08:30 广告异常复盘（默认任务说明）

异常按产品衡量（所有者要求，2026-11-25）：先在 campaign 级找出候选，再看候选 campaign 的主推产品（花费最多的 ASIN）以往的数据和它的价值、类型，判断是否真的异常、有多严重。

- 产品价值：客单价 = 基准期（前 7 日之前的 30 天）广告销售额 ÷ 广告订单，没有订单时用售价（`asin.asinPrice_`）。单笔允许花费 T = 客单价 × 目标 ACOS（没有给定时用该店近 30 天 ACOS），这是 SparkX Skill 的「高花费零出单」规则，不再用固定的 $50：贵的产品允许多花一些才算异常，便宜的产品少花一点就提醒。
- 产品历史：基准期的 CVR、ACOS、CPA；基准期广告订单少于 3 单视为样本不足，只按 T 判断。
- 产品类型：SP 上线不足 90 天的新品、客单价 ≥ $150 的高客单产品照常判断，但标注「新品期」「高客单」并降一级；季节性明显的类目注明。
- 托管组里的 campaign 由 SparkX AI 调价，只给托管组层面的建议，不给出价数字（Skill 规则）。

| 类型 | 判定（金额为 USD） | 建议 CPC |
|---|---|---|
| 全店零曝光 | 两周没有任何曝光，且仍有开启的 campaign | — |
| ① 高花费零出单 | 近 7 日广告订单 = 0，花费 ≥ T，且点击 ≥ 2 ÷ 基准期 CVR（按产品历史本应出 2 单以上） | 当前 CPC × 70% |
| ② ACOS 明显恶化 | 近 7 日花费 ≥ T，ACOS ≥ 产品基准期 ACOS × 1.5 且至少高 15 个百分点 | 当前 CPC × 基准期 ACOS ÷ 近 7 日 ACOS，一次最多降 50% |
| ③ 加预算后销售反而下滑 | 花费 ≥ T 且较前 7 日 ≥ +30%，广告销售额 ≤ −20%（或归零） | 收回新增预算 |
| ④ 异常停摆 | 开启状态，前 7 日花费 ≥ T，近 7 日无曝光 | 查预算、断货、限流 |
| ⑤ 低花费高转化（机会） | 花费 < 3T、广告订单 ≥ 3，ACOS ≤ 产品基准期 ACOS 的 70% 且不高于店铺 ACOS | 可加预算或出价放量（不计入异常） |

同类问题按浪费的金额排序（花费 − 广告订单 × 产品历史 CPA）。按类型的表格列：店铺、Campaign、主推产品、客单价、近 7 日花费、点击、广告订单、ACOS、产品历史（基准期 CVR / ACOS）、建议、运营。

结构：开头一句统计；一、最严重；二、异常店铺总览；三、按问题类型看具体 campaign；四、建议动作。两条任务说明都可以在管理台改写，改写后可先「预览」再保存。2026-11-25 实测（19 家店）：约 3 分钟，SparkX 12 次，DeepSeek 约 82 万 tokens（其中缓存命中 65 万），比按 campaign 判断时多约 50%。

## Excel 文件

每条日报、复盘和实时监控消息后面都跟一条同内容的 Excel 文件消息（所有者要求，2026-11-25），发给这条消息的同一批接收人（通知群、负责人、运营私聊）；测试发送也带 Excel，文件名前加「【测试】」。

- 文件名带日期：`广告日报_2026-11-24.xlsx`、`广告异常复盘_2026-11-18至2026-11-24.xlsx`、`广告实时监控_2026-11-24_1705_美西.xlsx`；运营私聊的只含其店铺的版本在后面加运营名字。
- 内容就是卡片的内容：「摘要」工作表写标题、统计日期、生成时间（北京）和正文；每张表格一个工作表，第一列是统计日期（多天的表可以直接拼在一起），金额、百分比、订单数是数字（可求和、排序），表头冻结并带筛选。
- 保存在服务器 `data/reports/<daily|review|hourly|tests>/<月份>/`（0600），不删除；管理台「发送记录 → Excel 存档」可下载最近 80 个。
- 发送时先把文件上传到飞书（不发任何消息），再发文件消息；文件和卡片一样先写投递意图、不重发。排队后文件被改动或丢失，这条 Excel 不发送（「已跳过」）。飞书拒绝上传时记为「飞书拒绝」并写明原因（例如应用缺少 `im:resource` 权限）。Excel 生成失败不影响卡片本身发送。

## 每小时实时监控

每小时读取美西当日截至目前的 campaign 数据（SparkX 当日累计，订单归因会延迟数小时），只看开启状态的活动：

| 类型 | 默认判定（管理台可改） |
|---|---|
| 高花费无转化 | 花费 ≥ $30 且广告订单 = 0 |
| 高花费低转化 | 花费 ≥ $30，有广告订单但 ACOS ≥ 60% 或 CVR < 5% |
| 低花费无转化 | $10 ≤ 花费 < $30，点击 ≥ 15，广告订单 = 0 |
| 低花费高转化 | 花费 < $30，广告订单 ≥ 2 且 ACOS ≤ 20%（放量机会） |

- 同一活动同一类型每个美西自然日只提醒一次；活动升级到另一类型时再提醒。当天已提醒的活动会告诉 DeepSeek，不再重复列出。
- 只在管理台设定的北京时间段内运行（默认 09:00–24:00）；排队超过 50 分钟仍未发出的提醒作废，不补发。

## 发送与核对

- 卡片在排队时冻结，同一接收人、同一天（实时监控为同一小时）只排一次。
- 日报和复盘只在北京时间 08:30–12:00 发送，生成窗口 08:30–10:00；SparkX 或 DeepSeek 失败时每 10 分钟重试，最多 6 次。
- 每次发送前重新核对：通知仍开启、该发送对象仍开启、仍在发送时段、负责人未更换（按绑定代次）、运营仍对应这些店铺且仍在通知群。不满足就保留记录不发送。
- 发送前先写入投递意图；之后若出现超时等不确定结果，标记为「可能已提交」，不自动重发。
- 飞书明确拒绝（返回错误码）时记为「飞书拒绝」并写明原因，同样不重发。常见的是 code=230013：接收人不在飞书应用的可用范围内（或已离职），需要在飞书开发者后台「版本管理与发布 → 可用范围」把此人加入并发布版本，之后私聊才能送达。
- 旧版本遗留在发送队列里的消息不会发送，保留为「已跳过」。

## 管理台测试发送

「通知与报告」里每条通知都有「预览」和「测试发送」。预览在后台生成（不排队、不发送）；预览窗口底部可以把这份预览发送到通知群和/或负责人，可选同时 @ 对应运营：

- 发送的就是预览里的卡片（服务器保存的那一份，浏览器不能改内容），只在标题前加「【测试】」，正文与预览相同，后面跟同内容的 Excel（文件名带「【测试】」，存在 `data/reports/tests/`）；不会再调用 DeepSeek。勾选负责人时发给这条通知的每一位负责人。
- 使用独立的记录（`jx:test:…`、`sync_jobs.job_type=jx_test`）：不计入当天的定时发送，不影响实时监控的「每天一次」去重，也不受该通知开关和 08:30–12:00 发送时段的限制。
- 发送前仍核对接收人（通知群未更换、负责人未变更、运营仍对应且在群内）；排队 30 分钟内没发出就作废。同一份预览发给同一对象只发一次。
- 服务器处于演练模式（`APP_DRY_RUN=true`）或未开启飞书发送时，管理台直接提示，不排队。

预览在服务器上保留 30 分钟：关闭预览窗口后再点「预览」，正在生成的继续显示进度，已生成的直接显示结果；修改任务说明或阈值后会生成新的预览，只改开关和发送对象不会。需要最新数据时点「重新生成」。同一时间只生成一份预览。
