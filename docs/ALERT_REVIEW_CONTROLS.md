# 飞书通知与 DeepSeek 审核

## 为什么按这几层拆开

- [Prometheus 告警规则](https://prometheus.io/docs/prometheus/latest/configuration/alerting_rules/)区分待确认和已触发；JX 的数据不完整、归因未成熟、源时间未核实都不等于业务异常。
- [Alertmanager](https://prometheus.io/docs/alerting/latest/alertmanager/)把问题检测与分组、静默、去重、投递分开。JX 保留收件人路由、夜间静默、去重及事务发件箱；模型不能指定发送对象，也不能改任何广告。
- [Grafana 通知模板](https://grafana.com/docs/grafana/latest/alerting/configure-notifications/template-notifications/)把呈现模板和告警判断分开，并提供预览。JX 用固定模板展示已验证的数据和先查项，不直接发模型自由生成的数字或结论。

```text
源数据 → 确定性资格和归因窗口 → DeepSeek 复核候选
       → 重读证据和白名单 → 固定卡片 → 发件箱 → 送达记录
```

## 使用与验收

1. 运营台由所有者配置 DeepSeek。凭据不应回显给浏览器、提交至仓库或粘贴到聊天。先在测试环境用一个已授权店铺、同一个明确日期和同一币种对照实际数据。
2. JX 审核 Skills 是内置、受审查的规则预设，不是第三方代码，不安装或运行 SparkXAI 市场 Skills。现有店铺、广告类型及活动覆盖设置不会因为切换默认预设而被清空。未确认真实流量、归因或门槛的店铺不要用模型补结论。
3. 先离线预览，不发送、不读写生产数据库：

   ```sh
   PYTHONPATH=src python scripts/preview_ad_alert_cards.py
   ```

   预览使用虚构数字和真实模板。第一行是日内预算观测，带店铺当地日期和明确采样时刻；第二行是成熟归因，带日期和归因窗口，真实订单和参考估算各自标注。实际有数据前不要将样例用于客户群。
4. 上线验收选一条日内与一条成熟归因广告，核对活动 ID、币种、当前值、比较窗口、及发送前是否仍然成立。另核对绩效源时间未知的账号：它可以显示历史观测，但不应断言当前异常。只有投递状态、没有卡片和证据，不足以判定历史误报。
5. 生产部署必须单独授权，记下实际运行版。回滚回上一已知应用版本，不删除数据库、发件历史或任何数据卷；不要为了回滚重发历史通知。后台配置记录也应备份，退回旧版前按实际部署的凭据文件格式复核兼容性。
