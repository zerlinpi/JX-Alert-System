## 1. 系统做什么、由谁分析

系统只读采集领星业务数据，保存历史、比较经营和广告指标，通过飞书发送日报或有证据的异常。系统不自动暂停广告，不修改预算、竞价、Listing或店铺设置。

```mermaid
flowchart TD
    A[领星只读接口] --> B[限定店铺与报表日期]
    B --> C[原始响应、事实、覆盖与版本入库]
    C --> D[规则初筛与实质性门槛]
    C --> E[Chat MCP读取冻结证据]
    C --> F[群内真实@或已授权私聊：DeepSeek分析]
    C --> G[分区Excel与每日全历史快照]
    D --> H{当前业务通知模式}
    H -->|rules| I[满足门槛的规则通知]
    H -->|chat| J[保留初筛事件，等待Chat分析提交]
    E --> K[提交前重验事实、成熟度与门槛]
    I --> L[持久通知队列]
    J --> K
    K --> L
    C --> M[08:00独立日报]
    M --> L
    L --> N[飞书接口与实际送达日志]
    F --> O[原消息话题内：真实数据表与简短分析]
```

三种分析入口必须分开理解：

| 入口 | 谁作判断 | 是否自动采集 | 何时向群发消息 |
| --- | --- | --- | --- |
| 定时流水线 | 服务端规则与数据保护 | 18:30任务执行采集 | 线上为`chat`模式，普通业务初筛不自动推群；店铺授权/同步状态、绩效数据质量提醒独立保留 |
| ChatGPT MCP | ChatGPT分析冻结证据，服务端校验提交 | 只有显式调用采集工具才采集 | 有证据且通过最终门槛的提交才入队；无异常提交空数组保持静默 |
| 飞书群内/私聊机器人 | 服务端生成数据表，DeepSeek只读分析证据与情景预估 | 不发起采集；采集/刷新要求提示使用后台同步 | 群内回原话题，私聊引用原消息；不等同自动业务告警 |

服务端没有自建“每小时调用ChatGPT/DeepSeek巡检全店”的定时任务。用户在外部ChatGPT建立的任务是否启用，不在本服务可见范围内，不能仅凭调度器开启就宣称外部每小时分析已执行。

| 绩效/业绩通知 | 自动采集并观测归档；`observation_only=true`，业务健康告警仍关闭 |
| 绩效无偏移源时间的时区配置 | 空，不将服务器时区代入源时间 |

| Excel | 分区归档及每天23:30全历史快照均开启 |

单店有两个独立开关：

- **停止采集**：每页请求及每次重试前读取已保存开关，停止下一请求；已经发出的请求可能完成，已提交历史保留。中途暂停记为跳过，不当失败重试。
- **停止通知**：停止该店自动/排队通知；重新开启不补发停用前旧排队消息。用户主动@机器人的原话题回复属于显式交互，仍可回应。

开关文件或单店条目缺失时，底层兼容默认开启；配置损坏时拒绝猜测。机器人、运营台、分析提交及主动采集按显式店铺范围校验。MCP底层只读查询可读取已保存的范围外历史；`collection_scope`不是统一的数据库行级读权限，MCP是单所有者授权读库。通知回退不授予任何人采集或管理权限。

## 3. 四种时间与报表日期

### 3.1 用户已确认的源时间口径

**采用领星接口返回的原始时间：保留源值，有明确时区信息才换算；不把服务器当前时间或北京时间套到未标时区的源时间。**

| 时间 | 用途与处理 |
| --- | --- |
| 领星源更新时间，如`update_date`、`lastUpdateDate` | 原始响应保留源值；标准化文字可去除首尾空白，但不改写源时区 |
| 源值自带`Z`或`+08:00`等偏移 | 按该偏移解释，再换算UTC比较新鲜度；显式偏移优先于额外配置 |
| 源值没有偏移 | 只有已有、另行核实的该数据源时区才可解释；没有则展示原文并标源时区待确认 |
| 系统采集时间`captured_at` | 另存UTC，用于证明何时取得观测；不能代替源更新时间 |
| 店铺报表日期`report_date` | 保留接口报表日及其站点口径；日期不是可随意换算的UTC时间戳 |
| 北京投递日/归档日 | 决定08:00日报、18:30计划、23:30快照属于哪一天，不代替业务报表日 |

接口响应时间`response_time`独立记录。店铺日报日期使用 `America/Los_Angeles`。绩效仍仅用于观测归档。领星无偏移更新时间保留源值，在精简早报标注“时效待确认”。

不支持的时间写法、无法解析的时区缩写或未标单位的数字时间，不自动猜测其含义；原始响应仍保留供核查。

本次核对的142条绩效历史更新时间均未带偏移，因此保留原文后仍不能自动验证源时间新鲜度。未来接口若返回明确偏移，本次修正允许直接使用，不必再人为补一个时区。

### 3.2 如何选择采集日

- 已核实时区的店铺：`D=该店本地当前日期−1`，即最近完整自然日。
- 未核实时区且保守历史模式开启：`D=UTC−12当前日期−1`。这是全球已结束日期的保守下界，不把UTC−12写成店铺真实时区。
- 未核实时区且保守模式关闭：标`WAITING_TIMEZONE`，不猜日期。
- 指定日期不能晚于该店当前允许的完整日期；采集任务首次计划会持久化，跨午夜重试仍沿用原计划。
- 未核实时区的店铺，问“今天/昨天/前天”需要改用明确`YYYY-MM-DD`；不据此启用盘中判断。

例如：2026-11-15北京18:30，未核实时区店铺的保守采集日是11月13日；11月16日北京08:00的查询目标日可能已到11月14日。日报必须写出目标日与实际展示日，不能将13日数字冒充14日。

### 3.3 历史展示与失败保护

默认查询日完全没有尝试、覆盖或事实时，可在前七日找同一天完整采集的销量和SP/SB/SD活动日报，并标明“查询目标日/实际展示日”。用户明确指定日期、目标日采集失败、已有部分事实或覆盖时，不静默换成历史日。未来/未结束日期遮罩业务判断，不能当作最终数据。

## 4. 采集、完整性与金额口径

### 4.1 已接入的数据

| 数据集 | 粒度与用途 |
| --- | --- |
| 店铺列表、商品、活动、广告商品主数据 | 店铺状态、名称、国家、MSKU/ASIN、活动及广告状态、预算、广告账户资料 |
| 店铺经营、ASIN、MSKU销量 | 订单、销量、销售额；店铺汇总从ASIN粒度汇总，不再加一遍MSKU |
| SP/SB/SD活动日报 | 活动级花费、点击、曝光、归因订单/销量/销售额，是广告日报汇总来源 |
| SP/SD广告商品日报 | 广告ID粒度，再关联MSKU/ASIN；不能与活动日报相加 |
| SB创意、投放、归因购买商品 | 独立明细分区，保留各自指标，不冒充SB商品级花费报表 |
| SD定位、已购买商品 | 独立明细分区，不与活动总额重复累加 |
| 独立SP日报/小时/广告商品/投放验证 | 显式活动范围，保留版本、原始页、匹配状态和逐项差额 |
| 绩效列表、绩效详情、业绩通知 | 源评分、评级、七项绩效指标及标准、通知处理状态；当前仅观测归档 |

活动和商品广告一般刷新22日；SB/SD扩展明细默认刷新最新完成日及其前14日的检查点，不是22日每天全部扩展明细。单店内步骤分别提交，后续失败不抹去已成功保存的分区。

活动主数据完整同步后，旧活动若本次未再返回，记为`not_returned`，不继续沿用旧`enabled`状态参与规则无转化判断。完整分页、返回结构和实体关键字段均需校验；嵌套参数签名仍须有官方依据，未核实的复杂签名继续拒绝。

签名规范化有明确白名单：目前仅`spAdvertiseHourData`与`spTargetHourData`的`campaign_ids`数组有端点专用处理。元素必须为正整数，与单个`campaign_id`合并去重后最多50个；Advertise另外限制原始数组最多50项。签名副本使用紧凑JSON文字，实际请求体保留数组，不把签名用的文字冒充请求字段。其他未核实嵌套值仍拒绝，不新增猜测算法；也可使用单个`campaign_id`验证接口。详见[client.py](../src/jx_alert/lingxing/client.py)及[签名回归](../tests/test_lingxing_signature.py)。

### 4.2 五种必须区分的状态

| 状态 | 含义 | 可否说正常/零 |
| --- | --- | --- |
| 尚未采集 | 没有该日期维度的采集证据 | 不可 |
| 接口无记录 | 请求完整成功，但源记录数为0 | 不可把每项业务指标补成0 |
| 真实零 | 有有效源事实，字段明确为0，覆盖与币种等条件有效 | 可显示0；是否正常还需规则判断 |
| 采集失败/响应无效 | 请求、分页、结构或必需指标校验未通过 | 不可；保留失败及已收到的证据 |
| 授权异常/源店铺缺失 | 无法正常获得该店数据 | 不可；不能排除在外后宣称全店正常 |

`data_coverage=COMPLETE`表示该分区请求过程完整，不保证存在非空业务事实，更不允许把缺失字段补零。店铺汇总行也不能凭空伪造“有一条记录”。

广告汇总要求相关SP/SB/SD源分区完成，并验证已保存实体数足够。完整成功但空记录的维度不新增虚构事实；其他维度存在完整真实行时可计算已有事实合计，但明细仍保留“接口无记录”。全部为空时指标仍未知，不能把可计算汇总理解成每个空维度都已证实真实零。

### 4.3 币种与日报/小时

- 广告账户币种已按用户确认使用USD；金额通知门槛只适用于明确USD证据。每条金额事实仍需有币种，空值不能当美元。
- 店铺总销售额的币种独立取实际证据；不能因为广告账户为USD就假定跨国店铺总销售也为USD。
- 不混币种相加；也不把归因广告销售额与店铺总销售额相加。
- 日报用于日结算/归因分析；小时数据用于盘中观测和对账。活动、广告组、广告商品、投放四种小时维度分别比较，不相加。
- 对账保留真实差额，不造补差行。SP负曝光等无效指标保留原始证据，标响应校验失败，不擅自取绝对值或改零。
- 独立SP区分无记录、活动未匹配、匹配且零花费、请求失败、响应无效；无可比指标时差额为不可比较，不是0。

## 5. 指标公式与归因成熟

### 5.1 七项广告指标

| 指标 | 公式 | 单位/范围 |
| --- | --- | --- |
| CTR | 点击÷曝光 | 比率，展示为百分比 |
| CPC | 广告花费÷点击 | 每次点击的金额 |
| CDR | 广告归因订单÷点击，采用领星CVR口径 | 比率，展示为百分比 |
| CPS | 广告花费÷广告归因销量 | 每件归因销量的金额 |
| ROAS | 广告归因销售额÷广告花费 | 倍数，不是利润率 |
| CPA | 广告花费÷广告归因订单 | 每单金额 |
| TCOAS | 全部广告花费÷店铺总销售额，采用TACOS口径 | 仅店铺全部广告汇总适用 |

参考比率采用“参考期分子总和÷分母总和”，不平均每天的百分比。分母为0时比率未定义，不显示0或无穷大。金额指标要求币种完整一致；当前值、参考值、比较基准及实际日期分别保留。

### 5.2 对比日期

| 对象/指标 | 本期日期 |
| --- | --- |
| 店铺经营，广告花费、CTR、CPC、TCOAS | 最近允许的完整报表日D |
| SP活动/商品广告的归因订单、归因销量、归因销售额及CDR、CPS、CPA、ROAS | 成熟日`T=D−7` |
| SB/SD归因指标 | 成熟日`T=D−14` |
| 店铺混合广告的归因类KPI | 保守使用14日成熟等待，不能因为主要是SP就混成D−7 |

优先比较本期与此前七个完整日。七日数据或币种条件不足时，仅在本期和精确前一日都有有效事实时回退前一日；不选择任意“最近有数据的一天”。完整七日方案同时覆盖最新和成熟日期时，SP最远需要D−14，SB/SD最远需要D−21，因此默认回刷22日。各指标独立校验，不能用未成熟当天转化替代成熟日。

原始数据表仍可列D日尚未成熟的归因观测，成熟约束针对比较与风险判断；不能把“展示观测”误解成“已作最终转化结论”。

## 6. 初筛规则

初筛保留较敏感的候选与历史事件，**不等于马上通知**。下列为核对时与源码默认一致的基础值。

| 初筛项目 | 触发条件 | 事件/限制 |
| --- | --- | --- |
| 订单、销量、销售额变化 | 相对选定参考值变化至少15%；参考值至少1，按该指标自身单位 | 下降P1；正向增长原构造P2但不进入业务告警生命周期 |
| 广告高花费 | 本期花费≥20，且达到参考值1.30倍 | `high_ad_spend`初始P1，但从不直接发送“高花费就是异常”通知 |
| 广告零订单 | 活动启用、归因成熟、花费≥20、点击≥10、订单明确0 | `spend_no_conversion`初始P1；不要求历史必须有订单，但仍要有有效比较证据 |
| 低花费零订单 | 上述条件成立，且本期花费低于参考值50% | `low_spend_no_conversion`初始P3，不是小额测试必然浪费 |
| 预算消耗 | 日预算有效，花费达到日预算90% | `budget_consumption`初始P2，不等于平台超预算违规；实质门槛启用后不单独提醒 |
| 源超预算事件 | 活动资料`lastOverBudgetAt`属于报告日，且当日花费比较证据可用 | `campaign_over_budget`初始P1；最终发送还要通过日预算和金额门槛 |
| 七项KPI恶化 | 基础变化15%；CTR曝光至少1000，其他样本使用基础点击/花费门槛 | 实质门槛开启后，未通过的新候选转为`WATCH/观察`，不作为可提交的`ADVERSE` |

适用对象包括店铺、MSKU、ASIN、广告活动，以及已接入的SP/SD广告商品。规则引擎对订单/无转化要求当前对象启用；Chat/KPI分析可复核暂停/归档活动的历史事实，但会标“当前未投放”，不把历史花费说成仍在消耗。

这是运营注意力门槛，不是亚马逊平台政策、利润目标或必然亏损标准。线上已启用；原始数据与初筛仍保留。

| 销售额下降 | ≥30% | 至少少100美元 | 参考销售额≥200美元 |
| 花费增长的实质性检查 | ≥40% | 至少多30美元 | 本期花费≥50美元；单纯高花费仍不是独立告警 |

### 7.1 持续确认与严重例外

- 普通异常必须连续两个真实报表日期达到相对、绝对影响及样本门槛；同日重复采集十次不算十天。
- 七日参考连同实质性样本/币种条件都可用时，本期及前一日都与**同一份本期前七日参考值**比较，不是分别计算两套滚动七日。
- 使用前一日回退时，第二日确认需要再有前二日证据；缺少则不凑出持续性。
- 严重异常可单日提示：一般指标相对恶化≥50%、花费增长≥80%，并且绝对变化至少为表中门槛两倍，原样本/币种/成熟度保护仍须满足。例如订单少6且下降50%才满足这一严重例外。
- “连续确认”和规则事件“48小时升级”是两套机制，不能互相替代。

实质性闸门会独立选择可用参考期：即使初筛表格有七日字段，七日日均样本不足时闸门仍可尝试精确前一日。当前表格保留初筛比较字段，未额外返回闸门参考期数值；核查边界案例时需结合源日期和样本复核，不能把所有展示的七日参考字段都当作实质性闸门实际使用的参考值。

### 7.2 零转化及超预算的独立检查

- 成熟归因后，**明确零订单、至少30次点击、至少50美元花费**才具备零转化提醒条件；不把未知订单当0。
- Chat分析可引用完整连续七个成熟日期的零订单窗口，按该窗口花费和点击合计判断；不得任意拼日期或只挑有利数据。
- 有订单但单均花费恶化，需要完整成熟的花费/订单/点击比较，再通过CPA实质性检查；不因“只有1单”就直接判高花费浪费。
- 仅用掉90%预算不发实质提醒。源资料有超预算事件时，还需确认日预算类型、本期花费达到日预算120%、超额至少30美元。未知预算类型不硬判超额。

### 7.3 三个发送出口都受保护

1. 规则通知出口：先应用实质性门槛，再检查模式、通知开关和事件状态。
2. Chat通用异常提交：经营下降、成熟零转化或单均花费证据重验后，再过实质门槛；小变化仅记未达到可通知条件，不入队。
3. Chat七项KPI提交：只接受最终仍为`ADVERSE`的指标；`WATCH`、正常、改善和证据不足不发群。

Chat通用主题为订单异常、销量异常、销售额异常、花费异常、转化异常；标题进一步使用订单下降、单均花费上升、广告零转化等具体问题，不统一写成“订单异常”。

## 8. 店铺状态、绩效与数据质量

### 8.1 领星同步/授权状态

| 源状态码 | 解释 | 初始严重级别 |
| --- | --- | --- |
| 0 | 停止同步 | P2 |
| 1 | 正常同步 | 不产生该状态异常 |
| 2 | 授权异常 | P1 |
| 3 | 欠费停服 | P1 |
| 其他 | 未识别状态，不猜原因 | P2 |

对应事件为`store_status_not_normal`，恢复到1可恢复同一状态事件。它表示领星ERP同步/授权状态，不是亚马逊账户健康，不能互相代替。

### 8.2 亚马逊店铺绩效快报

| 指标 | 未达标方向 |
| --- | --- |
| 订单缺陷率、迟发率、配送前取消率 | 高于源标准 |
| 有效追踪率、准时送达率 | 低于源标准 |
| FBA订单缺陷率、发票缺陷率 | 高于源标准 |

标准动态使用领星详情返回的`standard`，不是在程序中硬编码所有店铺都用1%/4%/95%。百分比按百分点数值解释；值无效、标准缺失或超出合理百分比范围时保持待确认。恰等于标准只标“标准边界待核查”，不猜平台使用严格还是含等号的比较符。

上述0–100范围保护属于只读快报层。当前关闭的健康业务事件构造没有完整重复这一范围校验，未来若批准启用须另行核查，不能由页面校验反推全链路校验完全相同。

AHR分数没有人为设置健康分数线；`GREAT`只译“评级良好”，不直接证明当前健康。只读快报只有在正常授权、源时间有效、评级属于已识别健康类且七项指标均有效未超标时才可显示“健康”。有风险评级或有效未达标项可显示需关注；缺字段、边界或未知评级仍待确认。

**当前仅观测归档**：保存绩效、违规/通知观测和数据质量，不新增、更新、升级或恢复健康业务告警。即使时间变为FRESH，该开关仍不被自动解除。页面对观测的只读计算与“是否启用业务健康通知”不是一回事。

以下业务健康规则已有实现，但当前不启用：

| 事件 | 启用后需要的证据 | 严重程度 |
| --- | --- | --- |
| `account_health_at_risk` | FRESH、识别的风险源评级、关闭仅观测模式 | critical/suspended/deactivated类P0，其他风险P1 |
| `performance_indicator_breached` | FRESH、源观测违反对应源标准、关闭仅观测模式 | P1 |
| `performance_notice_pending` | 通知源时间有效、处理状态为1、关闭仅观测模式 | P1 |

该表列业务事件构造条件，不等于自动发送条件。即使日后另行批准关闭仅观测模式，当前`chat`投递模式仍会拦截这三类规则的自动发送；自动通知还需`rules`模式及通知、路由等其他闸门同时允许。

业绩通知状态：1待处理；2已处理、3无需操作才可恢复相关通知风险；0或未知不恢复。`isRead`只表示阅读状态，不代替处理状态。采集全部分页，不先过滤掉未知/未读/旧通知；每页源时间均须有效才能做业务处理判断。

### 8.3 仍会保留的数据质量提醒

`performance_store_performance_freshness`和`performance_performance_notices_freshness`分别跟踪绩效及通知数据的新鲜度：

| 状态 | 条件 | 级别/用途 |
| --- | --- | --- |
| FRESH | 按明确偏移或已核实源时区算得有效源时间 | 恢复自身数据质量事件；不解除健康仅观测模式 |
| STALE | 源时间距当前超过8小时 | P1，过期 |
| FUTURE | 源时间比当前晚超过5分钟 | P2，源时间异常 |
| NOT_CONFIGURED | 无偏移且没有有效的已核实源时区 | P2，保留原文展示 |
| MISSING | 缺失或无法解析源时间/数据 | P2 |
| FAILED、未知状态 | 最新源采集失败或新鲜度未知 | P2 |

较新的失败/空同步会遮罩旧健康观测的新鲜度；不会因为历史上有一条健康记录就称当前健康。数据质量与授权提醒不受广告金额门槛拦截，不能因“小问题静默”而把采集故障藏起来。

## 9. 异常生命周期与去重

| 状态 | 含义 | 发送行为 |
| --- | --- | --- |
| NEW | 初次记录或恢复后重新发生 | 仍须通过门槛、模式、开关及路由；不等于已发送 |
| ONGOING | 同一事件持续存在 | 通常只更新记录；初次轻微、后来首次达到实质门槛时可首发一次 |

| RECOVERED | 完整、同作用域证据证明恢复 | 经营/广告实质事件要求本次incident曾DELIVERED才发恢复；授权/数据质量有独立恢复规则 |
| CLOSED | 保留的人工关闭状态 | 当前没有开放的通用MCP关闭写操作 |

默认升级时限为`first_seen`起**48小时墙钟时间**，不是“第三个完整报表日”。级别P3→P2、P2→P1、P1维持P1；恢复前不自动降回。采集不完整、指标无事实或授权失败不作为恢复证据；仅已完整评估的实体才可恢复其自身事件。

规则事件有店铺/实体/规则幂等键；Chat通用异常按店铺/主题/维度/对象/报表日/目标群去重，KPI按指标与实际指标日去重。换一种措辞或小时任务再次提交不会产生同一日同一问题的新通知。不同真实问题、报表日、状态升级或收件目的地可有独立记录。

### 10.2 DeepSeek分析如何省量并保持证据

- 不给模型广告修改、Shell、任意工具、网络访问或对话历史能力，只给本次冻结数据。
- 可基于完整历史证据做趋势、原因假设与月末花费情景预估；假设、实际值与预测值分开。经营口径、所缺数据与预估约束见[经营日报与只读分析](BUSINESS_DAILY_AND_READONLY_ANALYSIS.md)。
- 数据表由服务端生成，保留订单、销量、销售额、SP/SB/SD数据、七项KPI、实际日期及健康观测；模型不重新编写整张表。
- 模型只取当前花费最高至多10个活动样本，保留活动总数及当前暂停/归档状态；不据此宣称全活动逐一巡检。
- 精简输入移除重复指纹、重复日期数组及展示元数据，保留数值、币种、日期、覆盖、样本范围及未知状态。
- 相同会话、相同发送者、相同原问题、相同模型/提示词/精简证据指纹，可复用原生成时刻起最多10分钟的成功分析。命中不续期；事实、日期、质量状态或策略变动使指纹改变；失败不缓存。
- 输出按冻结KPI状态过滤观察/改善条目；未问覆盖范围时不把固定样本说明当异常。模型声称无异常但有实质候选时，保留有证据的候选。过滤后仍有缺口时继续待确认。

限制必须分清：

| 限制 | 类型 |
| --- | --- |
| 用户问题≤1200字符 | 服务端硬限制 |
| 完整模型上下文≤128KiB；先校验再精简 | 服务端硬限制，超限不发模型请求 |
| 模型响应≤128KiB、有效最终文本≤6000字符 | 服务端硬限制 |
| `max_tokens=1536` | 发给模型API的输出上限 |
| 最多6条、总计500字、简洁中文 | 提示词要求，不是逐字硬截断保证 |

模型超限、凭据/余额/服务不可用等失败保留真实数据表和分析不可用提示；不把不可用回复缓存为成功。HTTP429/5xx仅额外重试一次，间隔0.5秒；网络超时不重复可能已计费的请求。模型不完整、工具调用、密钥回显、非中文或可执行内容被拒绝。温度0.2、关闭thinking；官方返回的数字用量可记录，凭据与请求头不记录。

Chat分析快照最多22个完整日、10000条事实，超过需按对象拆分；快照2小时过期。通用异常最多10条发现，KPI最多7项；提交时重验当前源值、coverage、币种、成熟度、日期、对象状态和规则版本。修订过的旧证据要重新获取，不能直接复用。

有证据的广告异常通过分析提交。精简模式下 `send_chat_report_to_feishu` 对普通报告返回 `SKIPPED`；需要经营内容时，可直接在群里 @机器人或私聊查询。

OAuth访问令牌默认15分钟；刷新令牌默认30日并轮换，正常刷新不应要求每15分钟人工重连。授权请求默认10分钟、一次性授权码2分钟；旧授权页不能一直重用。授权及令牌状态持久化，普通代码更新不重建所有者口令或OAuth数据库。

### 11.2 运营台

地址：`https://jxmcp.pacefitday.com/console/`。单所有者登录会话默认30分钟，与MCP的OAuth会话独立。可查看店铺/日期数据、映射店铺运营负责人，并分别切换采集与通知。写操作有来源/CSRF检查、版本比较和限频，避免并发覆盖。

「通知群设置」可从机器人已加入的群中选择替换当前日报/默认群，预览人员影响后确认保存，动态生效。只更新现有群别名，保留其他独立群路由；店铺/商品/管理层人员映射保留，新群@按已验证成员过滤，原管理员仅留新群交集。不将旧待发消息移到新群，也不主动重发当日日报。

群管理员、管理层等角色仍来自路由配置；不能把“能在页面映射店铺运营”理解成所有角色都已在页面维护或私信已验收。

## 12. 定时任务、失败重试与恢复

### 12.1 任务表

调度均显式使用北京时间`Asia/Shanghai`，不会因为保留领星源时间而改动。

| 工作 | 时间/间隔 | 去重与恢复 |
| --- | --- | --- |
| 全范围采集计划入队 | 每天18:30 | 北京日固定幂等键；同日不重复登记；默认销量回补2日 |
| 采集漏触发恢复 | 每分钟、服务启动时 | 只在计划后30分钟窗口补当天缺失计划；不是无限追溯漏采 |
| 采集任务派发 | 每30秒 | 执行持久队列、互斥锁、检查点和延迟重试 |
| 飞书经营日报 | 每天08:00 | 独立执行器读取已入库数据，不等待大型采集任务 |
| 日报恢复 | 每分钟、启动时 | 不提前08:00；内容/范围冻结复用，过北京午夜不跨日自动补发 |
| 通知出队 | 每10秒 | 每批最多5条，有持久重试与租约 |
| 分区Excel重试 | 每分钟 | 只重导已有数据，不为修复文件反复请求领星 |
| 全历史Excel快照 | 每天23:30 | 北京归档日，与源报表日分开 |
| 全历史快照恢复 | 每5分钟、启动时 | 可恢复近7日失败/中断计划，成功快照不重复生成 |

08:00首次生成后冻结内容、日期和收件范围。聚焦早报复用当天升级前已经冻结的记录。精简模式每天发绩效/违规快报和有实质问题的SP活动页。授权、采集进度和广告数据缺口可在运营台或向机器人查询。无偏移源时间保留原值，状态显示“时效待确认”。详细展示与回滚见[早间快报与自然提问](MORNING_BRIEF_AND_QUESTIONS.md)。

### 12.2 采集重试

单个领星请求还有独立的短重试：超时/网络故障、HTTP429/5xx及已识别的限流响应最多尝试5次，等待1/2/4/8秒，每次重新生成时间戳和签名；参数、一般业务错误或无效响应不盲目套用瞬态重试。请求层结束后，外层才判断采集任务的延迟重试。

首次失败至少等60秒，第二次至少120秒，最多3次。锁忙不算领星失败、不扣失败次数。首次店铺日期计划和已完成店铺/日期检查点保存，跨午夜或重启不跳日；尚未完整成功的店铺可能重新采集，事实按唯一粒度替换，不累计花费。

最早重试时刻不是保证执行时刻，仍受30秒派发、锁和上游限流影响。领星令牌由既有管理器使用私有缓存与跨进程文件锁协调；只按已配置契约获取/续约，避免多个服务抢用同一轮换令牌。它与JX MCP的OAuth刷新是两套机制，均不在文档或日志展示令牌正文。

| 结果 | 解释 |
| --- | --- |
| PENDING / RUNNING | 等待/执行中；PENDING可带最早重试时间 |
| SUCCEEDED | 完成 |
| SUCCEEDED_WITH_WARNINGS | 主采集完成但有数据质量待确认，不因此反复重采成功分区 |
| PARTIAL_FAILED / FAILED | 有部分成功或全部失败，已耗尽尝试；保留成功证据 |
| BLOCKED | 范围、授权、开关或配置条件需改变，不靠反复请求解决 |
| INTERRUPTED / SKIPPED等 | 明确中断或未执行，不能写成已成功 |

### 12.3 通知重试与真实送达

通知先入`notification_outbox`，然后`PENDING/RETRY → SENDING → DELIVERED`；失败最多8次，前七次失败后的等待为30/60/120/240/480/960/1920秒，退避算法上限3600秒，耗尽为`DEAD`。暂停为`SKIPPED`，过投递日日报为`EXPIRED`。发送结果按领取时间和次数做并发比较，旧worker不能覆盖新结果，旧结果另记`STALE_*`。

SENDING租约超时会恢复；租约为`max(300, feishu_timeout×20×5+60)`秒，默认20秒超时对应2060秒。复用飞书消息UUID降低重复；飞书已接收但数据库提交前崩溃仍可能重投，因此不是绝对恰好一次。

自建应用模式只有接口成功返回有效`message_id`，并持久记录`DELIVERED`，才可说消息已送达。配置正常、权限存在、入队或尝试发送均不算送达。

### 12.4 通知路由

应用模式不需要Webhook。普通定向告警按群管理员、店铺/商品负责人及管理层角色路由，管理层私信可独立按级别/状态筛选。人员缺失且回退开启时，只回退已验证日报群，不猜@；多个缺失角色回同群时合并目的地。

上述管理层路由属于服务端规则事件路径。管理层未显式配置筛选时，默认包含P0/P1/P2/P3及NEW/ESCALATED/RECOVERED；不能假定默认只发严重异常。Chat通用/KPI分析提交当前直接发目标群，不自动附带管理层私信。

群无效、角色映射格式损坏或路由不可读仍失败。每事件/目的地独立幂等，修复一个失败角色不重发已成功角色，也不自动批量重放历史失败。完整Chat报告不自动@，群内问答回复原消息；二者不能套用成普通告警已完成真实@验收。

新群通知持久保存群别名与变更版本；发送前发现目的地或版本失效则`SKIPPED`保留。旧版没有别名的队列按原群退役时间截止，不靠切回原群重放。私聊另做发送者权限检查，不当作退役群消息。正在发送的请求无法通过切群撤回。

### 14.2 当前边界

- “已启用64店”不等于64店都有授权、数据、成熟基线或全活动巡检结果；16店授权异常需在领星侧恢复。

- 当前绩效源历史时间无偏移，继续保留源时区待确认；健康仅观测开关不解除。
- SP投放小时负曝光、日报/小时统计差异保留待源确认，不人为补差、不擅自放宽校验。

- 活动样本及单店测试不代表全店、全活动验收；群内真人@收发、真实人员@/管理层私信须以实际投递日志验收。
- 有历史回放但没有人工真假标注时，误报率未知；不能因测试通过就宣称误报率为0。
